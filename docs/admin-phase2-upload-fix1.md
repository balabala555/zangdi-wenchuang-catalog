# V1.4.0 第二阶段「上传修复1」

## 排查结论

Windows现象：后台启动且可读取已有10件商品、磁盘空间充足，上传只显示通用错误，黑色窗口无细节。原500错误处理丢弃实际异常，不能仅凭这句话判定磁盘不足或用户权限错误。

代码检查发现：`admin/assets.mjs`生成全部照片后，以`fs.openSync(file,'r')`打开文件并执行`fs.fsyncSync(fd)`。Windows的FlushFileBuffers需要可写句柄，只读句柄可能失败；原代码在刷新抛错时未进入close，还可能让清理异常掩盖首个错误。该步骤位于原图保存、水印生成之后、最终照片归档之前，符合“列表可读、照片上传失败”的表现。

使用隔离合成照片夹具，模拟Windows拒绝只读句柄刷新的规则：修复前复现EPERM/fsync失败；修复后通过，并确认原图字节不变。此为已确定的跨平台代码缺陷，但没有取得用户电脑的真实异常日志或原照片，不能断言它是该电脑上传失败的唯一原因。还需Windows复测确认。

商品快照保存原有durable使用可写句柄，不存在同一只读刷新错误；上传成功前也不会提交商品编辑，没有改动原数据格式或重建商品库。

## 本次修改

- 照片刷新改用`r+`，不截断、不覆盖文件内容；刷新失败也在finally关闭句柄。
- 分环节标记上传接收、识别/组件、原图、尺寸/色彩、水印、压缩展示图、元数据、刷新和最终归档；商品保存错误标记关联校验或快照阶段。
- 未知异常记录安全错误编号、阶段、系统错误码、有限源码位置、Node/平台/架构/版本；不写入异常原始消息、个人绝对路径、照片文件名/内容、请求体、Cookie、CSRF或授权令牌。
- 私有日志：`%LOCALAPPDATA%\ZangdiCatalog\merchant-data\diagnostics\errors.jsonl`。黑色窗口同步打印脱敏信息；日志本身无法写入时，网页明确提示保留控制台同编号记录。日志过2MB另起文件，旧日志保留不删除。
- 自己本次上传临时文件清理失败会单独记录，不掩盖原失败，也不会把已归档照片的成功响应改成失败。已有照片不清理。
- 页面及启动窗口标记“上传修复1”，程序修订`20261121-admin-phase2-upload-fix1`，软件仍V1.4.0；不升级业务功能或重画水印。

4. 核对右上角显示**V1.4.0 · 第二阶段 · 上传修复1**，已有10件资料仍在。点击编辑“测试商品001”，用原来失败的同一张照片重试；上传成功后保存到本地，再重新打开检查照片。

所有版本仍从同一个仓库外私有目录读取商品库；这次升级不恢复旧JSON、不清空、不重新导入商品、不删除照片。关闭旧服务再开新版本，以免实际仍连接旧后台。
